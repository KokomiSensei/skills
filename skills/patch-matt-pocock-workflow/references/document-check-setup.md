# 文档检查 setup

## 1. 选择实现方式

检查项目技术栈、现有文档检查器、统一检查命令、提交钩子和 CI。展示具体推荐及其依赖，让用户选择：

- **现成工具**：优先复用已有工具；缺少时建议安装 [lychee](https://github.com/lycheeverse/lychee)。核实所选版本的本地链接与标题锚点支持，配置后按验收样例验证。
- **项目内实现**：依据 [检查规范与验收样例](document-check-contract.md)，使用项目技术栈生成或扩展检查器。复用成熟的 Markdown 解析和标题 ID 库，保存实现、依赖和必要测试到项目版本控制中。
- **暂不配置**：本次不新增或调整检查器，保留已有配置及维护说明中的有效检查入口；项目尚无检查器时，写明“尚未配置检查器；修改后人工核对引用”。

现成工具和项目内实现共用检查规范。工具无法满足某条规则时，展示缺口和适配建议，由用户决定；仅在通过对应验收后报告支持。重复执行时检查现有实现和配置，在原实现上更新并保留定制。

## 2. 确定运行入口

选择配置检查器时，建议将文档检查纳入已有 lint/check/verify；没有统一入口时提出适合项目的命令。再根据项目现状建议 pre-commit、CI 的自动运行方式，解释运行时机和失败效果，由用户选择。只授权独立命令时交付该命令。

运行 [验收样例](document-check-contract.md#验收样例)，再运行全项目检查。验收通过与项目存量问题分别报告。将最终命令、运行目录、必要安装步骤和已批准的自动运行位置填写到维护说明的“项目检查入口”；使用稳定项目命令，详细配置留在工具配置文件中。

## 3. 规范文档引用

所有分支均采用 Markdown 链接引用实际文件。安装时若需批量转换项目原有的反引号文件引用，展示转换范围、源位置及目标，取得一次确认后执行；已有明确选择时沿用。按上下文区分实际引用与命令、代码示例、变量和占位符，只转换范围内目标明确的实际引用并保留显示文字，含义不确定时询问。检查器配置选择与批量转换选择相互独立。

补丁自带的实际文档引用在安装合并时直接采用 Markdown 链接。目标路径按安装后的文档位置计算；日常编辑按文档维护说明处理本次涉及的引用。完成条件：选择已落实，维护说明可直接执行，引用迁移选择及未解决问题已记录。
